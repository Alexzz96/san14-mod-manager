# 特殊战斗事件：本地观察阶段

## 0.8.1：普通单挑已核实并启用累计

用户实测曹仁（第一参与者）对张嶷（第二参与者），曹仁获胜；同一结算中的伤势调用以曹仁为来源、张嶷为受影响者，张嶷伤势从 1 升为 2。完整原生调用链进一步确认：原生单挑模型先依据胜负选择双方顺序，两条调用分支都把胜者作为第一参数、败者作为第二参数传给结算函数。第三、第四整数参数是附带的后果和报告上下文，不应直接当作谁获胜。

本地 0.8.1 仅对已匹配的两条单挑胜负调用位置、已采样的后果类别 0、报告上下文 0/1、双方稳定有效身份及敵对势力累计。除了函数入口，还检查两条参数传递路径和伤势来源/目标方向的实际代码；不匹配时保留候选，不开启累计。存档使用规范化结果 0=actor 胜、1=target 胜；这条已核实路径因为 actor 已是原生选出的胜者，所以固定使用 0。0.8.1 的 F 页面支持次数、获胜、战败排序，个人明细及回合报告直接显示双方胜负。

已有 0.8.0 候选缺少完整调用上下文，暂不自动补算；从更新后新发生的已核实事件累计，成功保存后保留。双方换位、不同报告上下文、其他附带参数不误计胜负已由独立测试覆盖；真正的其他结算类型仍待游戏样本核对。

抓捕已取得蔡瑁俘虏罗宪的一份原生报告与状态变化对应样本，但在 0.8.1 中抓捕报告的归属校验尚未接入累计，仍保持候选。`OrdinaryDuelVerified=1` 表示本次启动的普通单挑代码与已核实规则匹配；`SpecialSemanticsVerified=0` 继续表示并非所有特殊结果已验证。

以下为 0.8.0 观察阶段的口径和后续验证计划。

0.8.0 先接入单挑结算与抓捕结算候选。尚未通过真实游戏的单挑、俘虏样本核对，因此所有新采集事件均为 `verified=0`，不会加入个人累计。已有杀敌数（敌方兵力减少，含伤兵）、击溃、自身覆灭等统计继续使用原有采集链。

## 当前记录与展示

- 单挑结算候选：双方武将编号和当时姓名、势力、日期、结算模式及原始结果，结算前后的武将状态、伤势；不猜测未知结果是否为平局或中止。
- 抓捕结算候选：被俘武将、原势力、状态变化、来源部队及主将、结算参数和返回值。来源部队主将是关联信息，不能直接等同于实际抓捕武将。
- 嵌套状态、伤势及部队移除事件保留父事件编号，便于核对同一次结算的后果。JSONL 保留失败尝试；武将个人明细仅显示匹配双方身份的单挑候选、首次转为俘虏且符合候选返回值的变化。
- F 武将一览新增单挑次数、获胜、战败、抓捕次数、被俘次数、抓捕不同武将列及排序接口。0.8.2 将这些字段放在“战斗统计”页，未经验证或未记录项以 0 显示；后台有效位和候选记录保持原样。底部武将档案已移除；完整观察记录保存在日志和特殊事件检查点中。
- 所有支持的势力都可采集，仍使用“战斗数据记录与战绩”开关。F 页面只在打开时刷新。
- 回合结束的战斗标签页也显示涉及自势力的特殊事件候选，标记“待核对，未计入战绩”。不在该页面混入其他势力之间的事件。

累计器已预留经过验证的事件接口：同一武将重复被抓分别算次数，不同被俘武将去重算人数。只有经核实的个人抓捕者、不同有效势力及有效武将身份才能累计；部队主将候选和未知来源不能计入个人抓捕数。未经验证的事件不应通过手工修改文件转为已核实数据。

## 存档与安全边界

新记录使用独立的 `SAN14ModManager/career/checkpoints/<存档内容 SHA256>.s14special`，格式版本为 1，CRC 校验内容。普通存档与自动存档沿用原有保存/读档调用链，依照成功保存后的实际存档内容绑定。成功读档恢复该存档的对应检查点；无检查点的旧档从此次接入开始，失败读档保留原状态，新游戏另起记录。不会改写游戏存档，也不改动 `.s14career` 格式。

记录上限为 4096 条；满后标注不完整并停止增加新累计，避免丢掉名单后仍声称完整。关闭采集、队列或读取异常标注缺口。特殊文件损坏或来源不明时不覆盖；完整卸载仅删除通过格式和校验验证的本项目检查点，未知文件仍保留。

两个新入口独立检查实际代码及 MinHook 能否接入；失败不关闭原有 14 个战斗、保存与读档入口。`battle-observation-status.ini` 的 `SpecialHooks` 是观察入口状态（单挑 1、抓捕 2、两者 3）；`SpecialSemanticsVerified=0` 表示语义仍待实测。没有 EXE 版本或整文件哈希门槛，但入口与对象布局仍需匹配。

## 下一轮真实游戏验证

1. 保存测试存档并退出，再安装本地包；重启载入后检查两个入口已加载。
2. 触发一次单挑，记录双方、胜负、日期与伤势；核对日志中的双方与原始模式/结果、嵌套后果。
3. 触发一次战斗抓捕，记录被俘者与原生提示中的抓捕者。区分实际个人、部队主将和势力归属；原生数据无法确认个人时，保留未知。
4. 重复抓捕、单挑失败或中止、非战斗俘虏处理分别验证，防止把同一事件或非战斗变化重复累计。
5. 同一测试档分别普通保存、自动保存，重启读取，以及回退到事件前存档，核对记录恢复与分支回退。

独立测试验证参数/返回值/LastError 传递、候选不累计、重复事件去重、抓捕次数与人数区别、存档回退、跨进程恢复、未知文件保留、容量上限与 F 页面排序。独立测试不代表游戏内事件语义已确认；只有上面的样本对齐后才启用对应累计规则。

## 后续可扩展内容

可沿同一事件接口继续核对战法实际施放次数、命中对象和异常施加者；吸收伤兵；武将受伤、战死与处决；攻占城市；探索所得与招募者。每种数据都应先区分来源角色、结算事实及未知归属，再纳入个人生涯，避免使用全局状态变化推定某个武将的功劳。

## 0.8.3：抓捕报告关联与持久时间线

新增已采样普通战斗抓捕路径的归属校验。三个函数体锚点核对原生来源主将、俘虏状态与报告调用；个人双方身份稳定、敌对势力、指定成功调用上下文、同一父事件报告中被俘者和个人抓捕者及转为俘虏状态全部相符，才以个人抓捕者累计。任何条件缺失均保持候选，不把任意部队主将当作抓捕者。`CaptureReportVerified=1` 仅表示启动时该适配代码锚点匹配，每个事件仍须完整验证；不代表所有特殊事件或所有抓捕路径都已支持。

时间线在双方武将详情显示日期、发生时城市／县府、对象和结果。特殊事件既有格式不变，新增独立 `.s14timeline`；载入没有时间线检查点的存档时可导入已有特殊明细，标注旧记录且不猜测地区。既有未核实候选不自动改为已核实，抓捕不同人数与单挑总数仍保留内部接口，F 表格不显示。普通单挑制胜／败北沿用已核实规则。新增抓捕适配和时间线的实机验证待更新后进行，独立测试只验证关联、累计与持久化实现。
