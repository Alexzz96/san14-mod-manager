# 战斗数据记录（0.7.0 战绩接入）

## 回合结束报告

回到地图规划界面后弹出一个报告窗口，“探索”“战斗”两个标签页分别滚动，默认显示战斗。保持纸色背景与陶土色强调色；点击正文或右上角 × 关闭，标签按钮只切换页面。F10 → 探索与回合报告 → 查看上一回合报告可重新打开当前进程的最近报告。自动搜索开始的 2 秒提示不变，探索成功和失败明细均保留。

战斗页仅含涉及自势力的事件。玩家军团与武将军团通过世界 +0xde40 的军团表映射到势力，涵盖同一势力的不同军团；不使用部队 +0x11 字节判定势力。记录事件发生时的映射，格式 6 新增 `player_force_id`、`source_force_id`、`target_force_id` 及双方结算后的势力字段。

每回合从已确认“进行”到下一次规划界面单独统计，不因首次载入弹报告，不继承前一回合数字。敌方之间的战斗排除；己方受到的无来源火伤计入己方损失，施放归属仍为未知。造成敌方兵力减少必须同时辨认原生施放者和敌方势力。战法计为“战法效果”，不把调度次数命名为成功施放次数。击溃事件仅接受已有样本验证的移除原因 1、目标兵力为 0、敌我来源明确的路径；吸收伤兵要求来源对象前后身份一致。击伤事件要求健康字段实际恶化到伤势等级，未变化的 setter 不计数。士兵阵亡、新增伤兵、武将击杀保持未核实。

探索与战斗结果按起始／结束日期码匹配，等待 250 毫秒合并后台同轮结果，每轮只自动显示一次。不把上一回合探索合到新战斗页；未开启的组件显示未采集。回溯日期、世界或玩家势力改变会取消尚未完成的统计。队列、读取或日志故障显示采集不完整。单回合最多展示 4096 条战斗明细，超出会明确提示，原始事件仍在战斗日志中。最近一回合报告暂不跨进程恢复；0.7.0 的 F 累计战绩另行绑定存档检查点，见 [存档战绩](BATTLE_CAREER.md)。

这一版恢复战斗采集，并补充技能施放者和目标的关系。只读观察游戏原始事件，不追加游戏指令，不改变战法、异常、伤亡或探索结果。现有 F 武将一览仍仅在打开时采集一次。

## 已接入的记录

| 记录 | 内容 | 统计边界 |
|---|---|---|
| 技能行动尝试 | 来源部队、主将、行动 ID、原生参数及返回值 | 行动尝试不等于成功施放；无效果的尝试保留 |
| 每个目标的技能效果 | 原生管理器中的来源、目标、战法表编号和名称、效果类别、行动关联 | 同一行动的多个效果不能重复计为多次施放；跨线程或延迟效果的行动来源可能未知 |
| 火状态变化 | 实际格子的火状态、占用部队、关联效果、是否与技能目标吻合 | 记录失败起火、起火、熄灭和延长；不把全局火格的管理者当作施放者 |
| 兵力变化 | 原生来源、目标、主将、前后兵力、伤兵候选字段、所在格火状态、效果关联 | 兵力减少不等于阵亡。`field18_raw` 是会再次被结算修改的中间字段，不能直接当作新增伤兵 |
| 原生伤兵生成比例 | 旁观既有 getter 的六个参数、float32 返回位模式，及返回时的伤兵扣减参数 | 正常部队伤害路径可离线核对生成量与扣减量；预测与快照一致才标为公式匹配，仍不直接认定阵亡人数 |
| 异常实际施加 | 原生来源、实际受影响部队、模式、请求时长、前后状态计时、所属战法与行动 | 实际目标可能与调度对象不同；失败、已有状态、施放者不匹配均保留，不能按调用次数累加成功次数 |
| 武将伤势与状态 | 前后健康及身份状态、来源对象、原生模式参数 | 尚未实机验证击伤、死亡模式与归属，不累加击杀数 |
| 部队移除 | 移除前后部队、原生来源、原因、关联事件 | 撤退、合并、入城等可能共用移除入口；不自动算作击溃 |
| 原生日志 | 原生文字及参数、所属事件 | 可能包含非战斗信息，仅作诊断证据，不按消息条数累加战绩 |
| 回合阶段及规划快照 | 确认进行、回到规划界面的日期码、当前活动部队 | 后台一次扫描最多 501 个部队槽；读取前后核对世界、日期和阶段。属于尽力获取的快照，不保证期间绝对原子一致 |

部队及相关武将对象保留 512 字节的前后原始副本，后续可离线辨认其他战法的异常位，无需为每个武将单独写采集代码。当前尚未解码混乱、挑衅、止步等所有异常，不声称已经完整记录全部游戏事件。

0.6.0 的实测纠正了两个字段假设：效果入口的对象可能是施放侧的调度对象；战法定义 +0x70 的十项数组是参数，而非类别列表。0.6.1 将事件格式升为 4，单列参数、调度对象与目标角色，旁观现有的原生类别 getter 调用及返回值，不新增游戏调用。具体火目标来自实际点火棋格的占用部队，来源验证为同一行动内施放者和原生调度来源一致。旧格式的 `effect_categories` 不应直接使用；离线报告用同一行动及实际点火记录修正这次样本的链条。

0.6.2 使用格式 5。伤兵比例通过 `wounded_generation_ratio` 记录，并与所属 `troop_change` 关联；`wound_rate_float_bits` 是 XMM0 返回值的原始 32 位表示，整数 `native_return` 对此类事件不适用。保留 NaN、负零等位模式，采集器不参与浮点计算。公式核对只接受已辨认的正常部队伤害调用、唯一对应 getter、有效参数和一致身份；火烧等外层可能清空伤兵的路径保持未知。原生算法先增加伤兵，再按兵力损失和全局比例扣减伤兵，所以伤兵净增量甚至可能为负数，不能据此判定此次没有生成伤兵。

`army_abnormal_application` 记录原生七个参数和部队 +0x23 至 +0x25 的对应计时字节。已观察止步对应模式 1、效果类别 3；混乱与挑衅名称来自静态分支推断，需分别核对游戏界面。来源必须与同一行动及效果的施放者一致；`abnormal_after > abnormal_before` 仅表示计时增加，不代表跨整个战斗周期的去重成功次数。当前采集范围为技能效果上下文，环境或其他独立入口的异常暂不保证覆盖。

单回合已确认：张嶷造成 5 点直接兵力减少并触发曹仁的 88 点火烧损失；曹仁造成张嶷 5000 点兵力减少，随后张嶷部队覆灭且本人轻伤。曹仁在覆灭结算后接收 263 伤兵，再受到罗宪攻击而增加 51 伤兵，最终 5258 兵、314 伤兵。用户核对了覆灭、轻伤及最终数字。伤兵吸收与自身新伤兵必须分开；兵力减少 5000 不能直接当作阵亡 5000。该样本的原始日志和核对结果保存在本地分析目录，尚未成为存档绑定的永久战绩。

0.6.1 实机还记录了王威“止步”后罗宪对应计时从 0 变为 15、曹洪“激励”后的字段变化，共辨认火矢、奋战、齐射、激励和止步。用户确认本次由手动继续推进战斗完成回合；不能因为两次进程的事件语义相同就认定载入自动回放。跨进程累加仍需存档分支与回滚绑定。0.6.2 新增两个入口通过独立测试，游戏内验收待进行。

数据包含历史字段 `raw_force`、主将 ID、部队槽号、对象地址、所在格及日期原始值。武将对象的 `raw_force` 来自 +0x118；部队对象保留历史采集偏移 +0x11，该字节在目前存档均为 0，尚不能当作所属势力。实际势力应另由主将军团／势力映射核对，不按这个部队字节归属伤害。`player_force` 在本观察模式中仍是历史字段名，值为玩家军团原始编号，不能直接与界面中的势力 ID 比较。归属按事件中的具体对象判断。

## 开关及文件

F10 → 更多拓展 → 战斗数据记录。也可在游戏目录的 `SAN14BuildLimit.ini` 设置：

```ini
[Observation]
BattleEvents=1
```

受扩展总开关控制；0.7.3 起新安装默认开启；已有配置仍保留用户选择。该开关控制 F 清单与原生详情条的新战绩累计，关闭期间不采集，也不能补算历史。日志位于 `SAN14ModManager/logs/battle-日期-时间-PID.jsonl`，状态位于 `SAN14ModManager/battle-observation-status.ini`。`Enabled=1`、`HooksReady=1`、`Fault=0`、`Dropped=0` 才表示采集正常。不是安装器的版本白名单检查。

事件在游戏线程复制进固定队列，后台写盘。队列容量 2048，单进程日志限额 256 MiB；溢出、文件错误或达到限额会停止本次采集并报告故障，继续正常调用游戏，不能把该日志当作完整一回合。重启后才恢复故障停用。每秒刷盘，突然结束进程可能丢失尚未落盘的尾部。关闭开关以后停止产生新事件，已有队列仍会排空。

彻底卸载会清理符合本项目启动头的战斗日志和状态文件；其他同名内容保留。需要保留的研究日志应先复制到游戏目录外。

## 离线梳理

```powershell
python tools/summarize_battle.py 'D:/Games/SAN14/SAN14ModManager/logs/battle-实际文件名.jsonl' --output 'D:/analysis/战斗报告.json'
```

生成 JSON 与同名 Markdown 表格。直接来源和嵌套的原生目标效果可以关联到主将的“已观察到的兵力减少”，不会命名为阵亡统计。

后续无来源的火烧伤害只有同时满足具体部队身份、所在格、持续火状态、先前有效起火、已知火伤回调位置，才保留“同一火实例候选来源”。它仍不计入生涯数字。熄灭、竞争延长、移除、对象身份变化、离开格子或回溯日期会使候选失效；不能用全局火管理器负责人分摊伤害。初次载入已经燃烧的格子没有已观察施放者，保留未知。

一次只分析一个进程日志，事件按 ID 还原进入调用的顺序；写盘顺序可能不同。日志在重启后仍保存，但离线分析不直接跨日志相加。0.7.0 另外旁观保存成功、完整载入和剧本初始化，以检查点恢复 F 累计数据；事件格式升为 7，新增存档名称、内容摘要及有效标志。

## 验证顺序

1. 载入地图，先检查 HooksReady、Fault、Dropped 及规划快照。
2. 普通攻击与火矢各一次，对比界面的技能名称、双方主将、前后兵力、伤兵及起火状态。
3. 回合结束再核对最终伤兵快照，区分瞬时中间字段与实际最终值。
4. 分别验证部队覆灭、正常入城／撤退、武将负伤及死亡，辨认原生原因与来源。
5. 核对 F 累计数据，再验证真实保存、重启恢复和旧档回滚防重复；独立测试不能替代实机验证。

独立测试覆盖参数、完整 64 位返回值、LastError、关闭状态透传、无效指针、队列并发／溢出、来源目标链、一个行动多个效果、延迟效果、其他格子、失败起火、原始前后副本，以及保守的离线归属。独立测试不替代游戏内验收。
