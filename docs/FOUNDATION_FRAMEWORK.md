# 基础框架与 Mod 界面整理

整理日期：2026-10-10。代码基线：0.10.12。

本文保留最初的分组与框架设计。后续已经开始实施，当前接入范围、缺失功能及验证结果以 [基础编辑框架实施记录](FOUNDATION_IMPLEMENTATION.md) 为准。完整首版尚未完成；旧电脑的验证记录不等于新功能已在本机验收。

## 已确认的定位

用户确认以下三个功能为稳定功能，也是后续开发的基础：

1. 自动探索。
2. F 键武将搜索。
3. 战绩统计。

个性修改、地图光环也属于基础功能，后续应整理为公共能力。

“基础”说明模块承担什么职责，“稳定”说明该功能验证到了什么范围，两者独立记录。将个性编辑和地图显示纳入基础框架，不自动意味着现有全部操作和新配置已完成实机验收。

当前光环绘制在主地图的部队头像外围。缩略小地图不是当前实现的绘制目标；以后若增加小地图标记，应复用身份和效果数据，单独适配坐标与绘制位置。

## 玩家界面建议

F10 和独立管理器采用相同的三个页面：基础功能、测试功能、设置。F 键仍直接打开武将清单，个性编辑仍从选中武将进入。

### 基础功能

| 界面条目 | 展开的内容 | 定位与当前边界 |
| --- | --- | --- |
| 自动探索 | 执行武将、返回天数、优先条件、探索结果 | 用户确认稳定；保留原生探索规则 |
| 武将查询 · F | 中文/拼音/首字母、筛选排序、详情入口 | 用户确认稳定；作为武将操作的统一入口 |
| 战绩与生涯 | 采集开关、累计战绩、时间线、原生详情战绩条 | 核心统计由用户确认稳定；后续新事件按各自验证范围发布 |
| 回合报告 | 探索与战斗汇总、上一回合重开 | 建议作为公共展示能力；新布局和新事件仍保留原验收状态 |
| 武将个性编辑 | 九个槽位、隐藏编号、添加/替换、结果反馈 | 用户指定基础功能；当前只有远矢预设，通用选择器待实现 |
| 地图显示 | 光环、悬浮效果说明、显示样式 | 用户指定基础功能；当前主要支持曹仁/AI 固定样式，自由样式配置待实现 |
| 部队数值查看 | 基础值、最终值、原生来源、插件贡献 | 建议纳入基础；当前曹仁样本应保留试验标记，通用化后逐步验收 |

同一页面允许标注“稳定”和“待验证”，界面只展示与玩家操作有关的状态。内部会话、队列、ABI、钩子名称等放在诊断信息中。

地图显示开关只控制显示；关闭光环或说明不改变部队属性。没有生效效果的部队不因开启显示而获得效果。样式预览如需新增，应与实际游戏效果区分。

回合报告重开入口应归属于公共报告服务，可以从探索配置保留快捷入口；关闭自动探索后仍能查看已有战斗报告。

### 测试功能

| 条目 | 使用的基础能力 | 留在测试区的原因 |
| --- | --- | --- |
| 百战精锐 · 曹仁 | 战绩条件、属性修正、名称显示、地图显示、读档恢复 | 特定角色的规则与增幅属于玩法；当前验证范围沿用既有记录 |
| AI 随机词条 · 禁军精锐 | 成功建队事件、独立随机数、属性修正、名称显示、地图显示、存档 | 新城市保底、实际战斗及完整回合仍待实机验收 |
| 扩展兵种 · 陷阵营 | 兵种目录、编成、军费、身份绑定、属性与特殊效果、存档 | 特定兵种的规则属于玩法；修改版 EXE 的直接交战减伤适配待完成 |
| 墙体连片上限 | 六邻格查询、势力归属、建造确认、提示 | 属于可选规则；本轮暂归扩展项，未将其作为公共基础或重新判定稳定性 |

测试条目展示简短的效果、当前可用状态和已知未完成项。测试功能建议在新安装中默认关闭；修改默认值时保留现有用户显式选择，不在升级中悄悄关闭已经开启的功能。当前陷阵营新安装默认开启，这一行为若调整需作为后续版本的明确变更。

如果增加“测试功能总开关”，它只控制测试玩法，不停用稳定采集、查询、公共存档处理或其他基础模块。功能关闭保留记录，重新开启也不补抽或补算停用期间的历史。

### 设置

保留安装更新、移除、卸载、目录与版本；诊断日志从 Mod 玩法列表移入设置。建议补充功能兼容状态、数据保存状态、数据备份/迁移入口。

底层服务不逐一暴露为玩家开关。例如关闭陷阵营玩法，不应撤销 AI 词条仍需使用的公共建队接入；关闭 F 窗口显示，不应停止战绩采集。

## 需要作为公共框架整理的能力

| 公共能力 | 已有代码 | 应补齐的职责与接口 |
| --- | --- | --- |
| 游戏接入与兼容能力 | plugin.c、各模块 install/validate、各 offsets | 汇总每项实际入口检查结果；能力可用性与用户开关分开；共享入口安装一次 |
| 会话与对象身份 | 各模块 world、epoch、部队槽位/序号校验 | 统一新开局、载入开始/成功/失败；统一武将/部队有效身份，杜绝跨读档与槽位复用串数据 |
| 武将与部队数据查询 | officer_model、army_model、battle_stats provider | 提供只读快照；中文/拼音查询、势力位置、基础属性与战绩复用同一身份和口径 |
| 游戏事件与战绩 | battle_probe、battle_stats、special_stats、battle_timeline、turn_report | 在现有有界事件队列上整理成功建队、移除、战斗、回合与存读档通知；新规则订阅已确认事件 |
| 游戏线程命令 | personality_edit、troop_runtime 的提交处理 | 统一请求、排队、身份/阶段/快照复核和结果；界面线程不直接调用原生修改函数 |
| 存档附属数据 | battle_save.inc、career、troop_store、ai_affix | 统一存档定位与内容哈希上下文、模块注册和失败处理；各模块保持独立格式和版本迁移 |
| 效果登记与属性合成 | army_buff、career_affix、ai_affix、troop_runtime | 效果使用稳定 ID、来源、持有者/本次部队、条件、持续范围与叠加组；明确合成顺序，保留原生基数 |
| 名称与称号显示 | affix_names | 统一显示前缀/后缀优先级、长度限制和冲突；显示名称与真实姓名数据分开 |
| 地图叠加与悬浮说明 | map_effects_model、map_effects_ui、map_render | 业务模块提交效果描述，公共层负责位置、样式、同帧绘制、界面遮挡、多部队和资源恢复 |
| 回合/详情展示 | report_model/ui、detail_model/ui、army_ui、portrait | 业务提供结构化数据；统一列表/详情和报告入口，头像缓存继续作为内部服务 |
| 个性编辑 | personality_model/edit/ui | 整理个性目录和槽位接口；新增/替换沿用原生 setter 与旧效果清理；通用选择、删除和撤销逐项评估后实现 |
| 兵种扩展 | troop_registry、data/troops.json、troop_runtime/store/ui | 定义目录与原生适配分开；声明需要的能力，缺失时说明具体效果；陷阵营作为第一个业务定义 |
| 功能登记与配置 | features、manager_ui、INI | 统一分组、成熟度、依赖、状态和选项描述；新增功能不重复编写绘制、点击、滚动和键盘分支 |

公共框架优先复用现有模块，继续维持一个 DLL。没有当前需求时，不引入任意第三方 DLL 加载器、脚本引擎或全量重写事件系统。

## 当前代码中最值得先整理的地方

### 1. 界面登记仍有重复分支

S14Mod 目前只有名称、描述、分类、action 和 children。manager_ui.c 又分别按 Mod 编号编写展开高度、绘制、点击命中、开关路由和键盘导航。

建议登记表增加：页面分组、成熟度、配置项描述、默认值、能力依赖和状态提供者。绘制/命中/滚动/键盘使用同一份布局结果。稳定 ID 和已有 INI 键保持兼容，暂不扩大或替换所有位标志。

成熟度与实时状态分开。例如“稳定”功能可以处于“等待载入”；“待验证”功能也可以正常“已生效”。状态还应区分已关闭、缺少依赖、入口不兼容和异常停用。

现有文案存在历史遗留：“探索与战斗分标签查阅”“关闭后暂停两个视图”等，整理界面时应与当前单页报告和实际子功能数量一并核对。

### 2. 公共显示依赖具体玩法

紫圈和红圈配置目前分别为 CaoRenHalo 与 AiAffixHalo，绘制与资格分支直接识别两种效果。应保留旧配置映射，再逐步增加公共地图显示偏好和效果样式登记。

业务定义“谁具有何种效果、名称、说明、优先级”，绘制模块决定“怎样显示”。关闭具体玩法后它不再提交显示效果；关闭公共显示只隐藏画面。修改颜色和光圈宽度等只影响显示。

### 3. 属性修正需要统一合成规则

当前曹仁与 AI 同类攻防增幅取最高，特殊兵种倍率另外应用。提取公共合成接口时先保持这一结果，再明确效果分组、应用顺序与冲突优先级。

任何插件修正均以本次原生计算为基数，不能反复使用已经增幅的缓存。白字/最终值的适用范围、编成预览/实际部队/战斗调用需显式区分；来源不完整时保留未解析说明。

### 4. 建队接入与陷阵营业务需要分开定位

AI 抽取现在复用 troop_runtime 的建队 hook，并依赖该模块接入就绪；它已经不依赖陷阵营的用户开关。后续应将成功建队与身份校验明确为公共能力，避免继续扩大以特定兵种命名的职责。

公共建队接入验证通过，只表示能获取事件，不代表军费、减伤、混乱免疫等其他适配全部可用。每项实际效果分别声明能力与验证范围。

### 5. 数据保存应成为一致的模块协议

现在战绩、兵种、随机词条均按原生存档内容哈希关联，但上下文、错误反馈与恢复流程分散。应建立模块参与的保存/恢复协议，统一当前会话和分支上下文。

载入开始暂停旧效果；成功后恢复相应模块；载入失败恢复原会话。各模块的损坏和未知文件按既有规则处理，不以某一个模块的缺失覆盖其他模块有效数据。

玩家应能看到新增数据是否已保存、缺少哪些附属记录，以及备份需要带走的目录。后续再扩展其他原生存档位置，不能猜测多个账号中的同名文件。

## 扩展规则的目标形态

以后新增一个战绩词条，主要描述：

- 稳定 ID、名称、成熟度、默认开关。
- 条件，如已记录斩敌达到阈值；条件读取既有战绩快照。
- 持有者，是武将还是本次出征部队。
- 效果，如攻军/防御倍率、同类叠加组和优先级。
- 显示，如称号、光圈样式、悬浮文字。
- 保存策略，是从战绩派生资格，还是保存独立状态。
- 实际所需的原生能力，以及对应验收状态。

示例流程：战绩快照达到条件 → 规则产生资格 → 公共属性层应用效果 → 公共名称/地图/详情层展示 → 公共读档上下文恢复。具体模块不另写一套姓名 hook、光圈绘制和存档定位。

上述是接口目标，目前代码还没有通用规则解释器。先支持类型化 C 定义或登记表，确有需求再考虑外部数据定义。

## 建议的实施顺序

1. **整理界面与元信息**：基础/测试/设置分组，单列个性编辑与地图显示，给待验证的基础子项保留标签；保持原配置兼容，统一文案与状态。
2. **整理公共上下文**：能力状态、会话身份、成功建队通知、游戏线程命令和存档上下文；维持三项稳定核心的行为与数据口径。
3. **提取公共效果与显示**：将曹仁/AI 的数值、称号、光圈/说明接入公共描述，保持现有倍率、优先级和存档结果。
4. **完善基础工具**：个性目录与通用选择、更多武将的部队数值查看、地图样式配置、数据备份/迁移。
5. **迁移和验收测试玩法**：以曹仁、AI 词条、陷阵营作为样例验证公共框架，再增加新的词条和兵种。

每阶段做可独立审查和回退的改动，不一次搬动全部原生接入。

## 改造验收重点

- 自动探索派遣条件、原生费用和返回逻辑保持；F 搜索/排序正常；战绩口径与旧数据兼容。
- 同一功能在游戏内和独立管理器显示相同分组、配置与实际状态，键盘和滚动可用。
- 测试玩法全部关闭时，三个稳定核心正常使用；关闭视图不停止采集。
- 关闭地图显示不改变属性；菜单/详情/读档/缩放后没有残留光环或旧身份。
- 不因共享 hook 的业务关闭而停掉其他模块；接入失败只停用确实依赖该能力的功能。
- 同类效果不重复增幅，反复打开详情和切换开关不累乘。
- 个性修改核对九个槽位与旧快照，只修改目标槽，游戏线程执行，结果与保存行为可追踪。
- 手动/自动保存、重启、旧档回退、载入失败和新开局分别核对，附属文件正确对应分支。
- 旧 INI、旧附属格式、未知配置与数据保留策略不被分组重构改变。

这些是后续实现的验收清单，本次整理没有执行编译或游戏内验收。
